## Úvod a kontext

Forge stojí na řetězení několika konkrétních slabin a artefaktů: `fuzz.forge.htb`, `admin.forge.htb` a Apache.

Důležitější než samotný exploit je tady interpretace mezikroků, protože právě z těchto indicií vzniká SSH se získaným soukromým klíčem a teprve na něj navazuje příliš široká `sudo` oprávnění.

## Počáteční průzkum

### Vyhledání otevřených portů

Nejprve mapuji veřejně dostupné služby, protože právě z otevřených portů odvodím, které protokoly a aplikace má smysl zkoumat detailněji.
```bash
ports=$(nmap -p- --min-rate=1000 -T4 $IP | grep ^[0-9] | cut -d "/" -f 1 | tr "\n" "," | sed s/,$//);echo $ports;nmap -p $ports -A -sC -sV -v $IP
```
```
PORT   STATE    SERVICE VERSION
21/tcp filtered ftp
```

## Analýza zjištění

### SSRF a interní administrační rozhraní

Na hlavním webu bylo důležité nejen najít další vhost, ale hlavně správně vyhodnotit, co znamená hláška `Only localhost is allowed!`. To obvykle ukazuje na interní rozhraní dostupné jen z lokálního hostu. V kombinaci s funkcí pro načtení obrázku z URL to dávalo smysl číst jako SSRF: pokud aplikace sama stahuje zadanou adresu bez dostatečné validace, lze ji přimět sahat i na interní služby.

```text
wfuzz -H "Host: FUZZ.forge.htb" -w SecLists/Discovery/DNS/subdomains-top1million-110000.txt --sc 200 http://10.10.11.111
=> admin.forge.htb

http://admin.forge.htb/
Only localhost is allowed!
```

### Přístup k FTP a SSH klíči

SSRF zde nebylo zajímavé samo o sobě, ale tím, co zpřístupnilo za ním. Interní admin rozhraní odhalilo přístupy k FTP a stejný server-side fetch šlo použít i proti lokální FTP službě. Tím se podařilo získat soukromý SSH klíč uživatele `user`, takže další práce už mohla probíhat mimo webovou aplikaci v běžné shell session.

## Získání přístupu

### Stabilizace přístupu přes SSH

Jakmile mám soukromý klíč, přechod na SSH je nejrozumnější další krok. Webová chyba posloužila jen jako vstup; SSH už dává stabilní terminál a dovoluje přesněji ověřit lokální artefakty i privilegovaná pravidla.
```bash
ssh -i id_rsa user@forge.htb
```

### Získání user flagu

```text
$ ssh -i id_rsa user@forge.htb
$ cat user.txt
__CENSORED__

$ sudo -l
    (ALL : ALL) NOPASSWD: __CENSORED__ /opt/remote-manage.py
```

## Eskalace oprávnění

### Získání root flagu

Root část nestála na chybě v SSH ani ve webu, ale na tom, jak se choval privilegovaný Python skript. Při vyvolání chybového stavu se otevřel interaktivní debugger `Pdb`, který už běžel s root právy. Jakmile je privilegovaný proces ochotný pustit útočníka do debuggeru, znamená to v praxi možnost spustit libovolný kód.
```bash
sudo /usr/bin/python3 /opt/remote-manage.py
cat root.txt
```
```
__CENSORED__
```

## Shrnutí klíčových poznatků

- Z hlediska rozhodování bylo nejdůležitější správně přečíst vazbu mezi `fuzz.forge.htb`, `admin.forge.htb` a Apache.
- K uživatelskému kontextu vedl konkrétní a ověřitelný krok: SSH se získaným soukromým klíčem.
- Poslední část ukazuje, že po získání shellu rozhoduje hlavně to, jakou roli hraje příliš široká `sudo` oprávnění.

## Co si odnést do praxe

- První obranná lekce míří na `fuzz.forge.htb`, `admin.forge.htb` a Apache. Webová vrstva nesmí publikovat víc, než je nezbytné; vedlejší vhost, debug endpoint nebo zapomenutý soubor často odhalí skutečný vstup do řetězce.
- Druhá lekce je o tom, jak rychle se ze zjištění stane SSH se získaným soukromým klíčem. SSH klíče nesmějí být sdílené mezi rolemi ani uložené v procesech, exportech nebo webrootu; uniklý privátní klíč je stabilnější foothold než jednorázový shell.
- Třetí lekce připomíná riziko, které v praxi představuje příliš široká `sudo` oprávnění. Široká `sudo` oprávnění je potřeba pravidelně revidovat; wrapper, install helper nebo diagnostický příkaz často udělá z běžného účtu roota.
